# Phase 2：生命周期接入与并发审计

> 2026-10-08。沿 Phase 1 的 lifecycle owner 接入 iOS 原生来源；本文区分源码行为与执行证据，不把 host 检查当作 Apple 编译。

## 1. 生产入口与所有者

| 路径 | 本阶段职责 | 状态、输入与输出 |
|---|---|---|
| Swift 原生事件源 | 在主队列观察 App/当前 Scene 相位，向注册的 Channel 回放并发送变化 | `active / inactive / background`、进程内单调 `nativeSequence`、`snapshot` |
| 插件 [`events.rs`](../../../src-tauri/plugins/vcp-mobile/src/events.rs) | 同一强类型解码和订阅入口同时编译到 Android/iOS | `NativeEvent::Lifecycle`、`NativeEvent::Network`；非法载荷不进入业务 owner |
| [`lifecycle_manager.rs`](../../../src-tauri/src/vcp_modules/infra/lifecycle_manager.rs) | Core READY 后安装原生订阅；回调只提交事实和排队 | 生命周期进入 controller；iOS 网络进入现有 Vue 恢复入口；订阅错误进入原 service failure owner |
| [`lifecycle_state.rs`](../../../src-tauri/src/vcp_modules/infra/lifecycle_state.rs) | 移动端共用原生排序器和已应用快照 | 首次真实来源之前 `lifecycle_snapshot = None`；不从默认前台布尔值制造快照 |
| [`lifecycle_controller.rs`](../../../src-tauri/src/vcp_modules/infra/lifecycle_controller.rs) | 在短锁内判断 native sequence，再分配 Rust epoch；在原 transition 锁内应用 | 写唯一快照并发出 `vcp-lifecycle-changed`，保持 native sequence 与 transition epoch 独立 |
| [`useAppLifecycle.ts`](../../../src/core/composables/useAppLifecycle.ts) / [`appLifecycle.ts`](../../../src/core/stores/appLifecycle.ts) | 复用 Phase 1 订阅、系统快照归约及已有恢复函数 | `transitionEpoch` 排序；浏览器可见性只影响渲染与恢复时机 |

`lib.rs` 已在 bootstrap 前注册 `LifecycleState`，其 WindowEvent 分支已排除 Android/iOS，本阶段无需再增加第二个入口。`lifecycle_reconciler.rs` 的 Distributed capability 检查沿用 Phase 1。

## 2. 启动与资源边界

1. Rust setup 先建立纯内存 owner；数据库、设置及 Sync owner 在 bootstrap 中就绪。
2. Core READY 后安装 Channel，Swift 随注册返回当前生命周期快照，补齐订阅之前的变化。开始订阅不阻塞 Core READY。
3. Swift 尚未提供真实状态时，`get_system_snapshot.lifecycle` 可以为 null；Vue 不把 null 写成一个原生 active 事件。iOS 的恢复门禁必须等到真实 active；Android/host 保留既有 null 启动语义。
4. Native 回调只进行短时 sequence/epoch 处理、事件投递和任务安排，不等待数据库、网络或同步原生命令。
5. 订阅失败经插件已有 `report_service_failure("events", ...)` 回报并记录，早于 UI 的错误可由系统快照读取。不存在“失败后伪造成功快照”的 fallback。
6. 原生 selector 的最终响应由插件桥接任务接收；外层等待取消不允许直接销毁 Tauri receiver。其实现及超时边界归插件桥接工作项，不在 lifecycle owner 再造接收器。

Swift 的 Channel、通知 observer、网络 monitor 与注册 generation 归原生事件源；Rust 的 transition task 不持有 UIKit 资源。场景状态与网络事实分别传递，网络未知不发送一个虚构的 `connected: false`。

Rust bootstrap 当前只安装一次订阅。原生注册超时后，已保留的任务仍可接收迟到完成；真实注册 reject 或 Swift 事件源失败后，当前恢复方式是用户重新启动应用，前端启动重试只重新查询能力，不重装 Channel。保持这一区别，避免把 capability 重试描述成订阅恢复。锁定 Tauri 的 `Channel::new` 会把 callback 放入进程全局表且无公开移除接口；本阶段单订阅有界，未来若增加重试必须复用原 Channel。

## 3. 排序与相位语义

| 场景 | 当前归约行为 |
|---|---|
| 初次注册时 sequence=0 | 原生排序器接受；“尚无事件”与“第 0 次快照”不同 |
| 重放相同 phase/sequence | 在分配新 Rust epoch 前拒绝；不会延长后台区间 |
| 同一进程重新注册 Channel | Swift 的 phase/sequence 不重置；注册快照复用已观察状态的 sequence |
| 真实 phase 变化 | Swift 递增 sequence；若注册时重新观察到变化，也按真实迁移递增 |
| 较旧 native event 晚到 | 在短锁内拒绝，不得淘汰新的待执行任务 |
| worker 执行顺序与回调相反 | 尚未开始的旧 epoch 被跳过；已经开始的 transition 保持原有完成语义 |
| inactive | 写入并广播相位，暂停交互动画；不触发 Android 后台租约，不将它等同于 background |
| iOS background / active | 更新原有前台布尔状态与快照；本阶段不新增 Chat/Sync 取消、重试或后台存活承诺 |
| Vue live event 先于旧系统快照 | 同一个 epoch reducer 拒绝旧快照 |

Android 原有 10 分钟 VCPLog linger、5 分钟 Distributed linger、恢复意图及租约路径保持。iOS 不编译这组 linger 状态和 controller 副作用；host 仍保持已有开发行为。

## 4. 网络事实的实际消费

iOS `NWPathMonitor` 产生已知 `connected` 后，经 `NativeEvent::Network` 发送 `vcp-network-changed` 事件，载荷为 `{ "connected": boolean }`。路径可用只表示原生观察到的网络事实，不等于目标服务可达，也不将完整 `networkStatus` 遥测能力标记为已实现。

Vue 收到 true 时复用现有 `checkAndRecoverInterruptedStreams()` 入口：仍要求 Core READY、文档可见、iOS 已收到真实 active 相位，并由原 `recoveryPromise` 合并重入。false 不发起恢复。新事件不建立 network store、连接副本、业务重试任务或终态 owner。迟到监听者依然由 READY、回到 active、文档可见及已有 browser online 入口进行现有对账，不依赖每一条网络通知都被 UI 收到。

审查发现原先 `phase && phase !== 'active'` 条件会让 null 通过：NWPath 回调可能先于 Rust worker 应用启动快照，在状态未知时启动恢复。已在同一恢复函数读取既有 platform store，仅对 iOS 要求已知 active；READY、native/browser online 和文档可见入口一起受此门禁约束。网络监听与生命周期监听分别安装，卸载时释放，异步注册晚于卸载完成时立即释放，迟到 callback 不能发起恢复。

Android 的 connected=true 仍唤醒既有 Distributed client，并由 capability 检查保证实际入口已实现；iOS 不进入这条 Android 专属业务链。

## 5. 三方审查落点

- **Melchior**：native sequence 必须先于 Rust epoch 判断；回调不能同步调用原生命令；Tauri 最终响应接收器不能随业务等待取消而销毁；初始 null、快照回放与迟到事件共用一个 owner。
- **Balthasar**：inactive 与 background 分开；当前 Scene 原生状态决定相位，document.hidden 不覆盖它；回到前台的界面恢复复用现有根生命周期，保留同一 overlay/session 状态树。
- **Casper**：扩展实际生产 cfg 和已有网络恢复入口，不建立第二套调度器；本阶段只接来源和桥接，Phase 3 再处理有界领域停止，Phase 5 再引入实际后台任务。

## 6. 验证及 Phase 3 交接

本工作项已进行逐分支源码审查和 `git diff --check`。主代理已执行相关 TypeScript 定向检查，7 项通过，包含新增网络恢复/null 相位、READY、inactive/background/hidden 及卸载边界。统一静态检查与 Rust lifecycle 回归由阶段验收统一执行并记录；不单独并发启动 Cargo 构建。既有排序、初始 null、快照身份及 linger 取消回归继续适用，无需按 cfg 文本重复新增测试。

Apple producer、UIKit/Scene、Swift selector 和真实 Channel 注册仍需 G1 的 Apple 编译/链接诊断；Windows host 检查不能提供这些证据。项目不新增 iOS 实机测试体系。

Phase 3 继续：iOS background 对 Chat/手动 Sync/持久连接的有界 cancel/stop/join/flush，以及回前台持久连接恢复。本阶段接入相位后，既有日志前台判断会随真实相位工作；业务收尾与后台日志冲刷策略尚须由 Phase 3 完整核对，不能把已接通事件当作该策略已完成。
