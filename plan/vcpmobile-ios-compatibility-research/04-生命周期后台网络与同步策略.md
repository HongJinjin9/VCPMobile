# 04. 生命周期、后台、网络与同步策略

> 2026-10-09 修订：SSE 后台持续接收按用户最新审批列为高优先专项；其他任务沿用尽力后台与明确收尾。审批来源见 [Phase 2 功能审议表](./phase-2/09-功能权限与提示审议表.md)，具体任务见 [08](./08-分期实施路线图与验收门禁.md)。

## 当前目标与技术方案的边界

用户要求重点解决 SSE 响应在后台持续接收，不能仅以原 D2 的“尽力后台”表述认定该要求已经满足。Phase 5 的 P5-1 先比较具体方案；用户提出的循环静音音频与 iOS 26+ continued task 均需沿实际 API、系统版本、音频会话/任务声明和中断条件核对，批准研究不代表已选择某种手段或证明其有效。当前源码尚无这条保活实现。

continued task 仍是已有研究路径：用户发起 Chat 后申请，系统接受并激活时由同一个 Rust 请求继续执行；低版本、提交拒绝、资源失效等路径保留前台常亮与有界收尾。该回退用于避免任务悬挂，不替代 SSE 持续接收目标。手动 Sync、Log/Info、Distributed 与维护循环各自采用尽力后台或明确退后台策略。

P5-1 必须交付每个候选的适用条件、资源持有/释放、中断与恢复路径，以及不能覆盖的情况。尤其区分“仍在接收同一 SSE”“连接已断后重新请求/对账”和“最终结果已经持久化”。若研究及实现仍不能满足连续接收要求，明确保留未关闭项和技术原因，不能用重新命名完成条件代替用户目标；Apple 编译成功也不能证明后台运行时保证。

### 研究输入与具体问题

Apple 的 [continued-task 说明](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados)给出了用户发起、系统 handler、进度、expiration 与完成通知的接入方式；[WWDC25 讲解](https://developer.apple.com/videos/play/wwdc2025/227/)说明 `.fail` 提交策略与动态任务标识。实现以这些接口和锁定 SDK 声明为输入。

continued-task 路径需解决的三个代码问题：

1. Rust 的生成 attempt 与 native task 共享身份和唯一完成者；
2. 服务端当前发送 `delta.content`，需要定义真实累计字符/字节、可选 token、终态与系统 `Progress` 的映射；
3. background 时其他连接和维护任务按各自策略停下，保留正在执行的用户生成。

任务主线：

```text
USER_START(attemptId)
  → REGISTERED → SUBMITTED → ACTIVATED(taskId)
  → 同一 Rust SSE + 真实累计进度
  → SUCCESS / USER_CANCEL / SYSTEM_END / TRANSPORT_ERROR

提交拒绝或 API 不可用 → FOREGROUND_ONLY → 退后台时有界收尾
```

### 进度适配

继续采用 D19：真实计量与明确 terminal。当前 SSE 可以在 Rust owner 统计已接收字符/字节和 chunk；服务端提供 token 时再增加 token 字段。总量以 `Option` 表达，`max_output_tokens` 保持预算含义。

- 领域 DTO 建议为 `attemptId / completedUnits / unit / totalUnits? / phase / sequence`，只由真实数据事件更新；
- UI 在总量已知时显示比例，在总量未知时显示累计数量与阶段；
- Swift 映射层独立处理 `Progress` 和系统标题，逐项查验选定 SDK 对 indeterminate、计数更新和 terminal 的处理；
- 需要补足的具体问题是“总量未知时，系统 `Progress` 如何表达活动进度并响应停滞”，检索入口为 `BGContinuedProcessingTask.progress`、Foundation `Progress` 声明及系统说明；提交、回调、取消和前台回退可同时实现。

Apple DTS 对[不定长任务的讨论](https://developer.apple.com/forums/thread/840384)表明该问题有实际适配空间，也指出系统进度 UI 与此类任务存在契合度问题。对本项目的推论是保留尽力后台研发，明确处理低进度导致的 system end。D19 的真实计量决定继续约束映射实现；该讨论中提到的合成进度做法不纳入本方案。

## 当前生命周期事实

- Android Kotlin 与 iOS Swift 已接入 native IPC Channel，Rust `events::subscribe` 支持两个移动目标；iOS 在核心 READY 后由独立任务等待事件注册的最终 ack。
- Swift 订阅 App/Scene 与 NWPath 事件，WebView 替换复用同一 Channel 并更换观察者 generation；只有事件注册 selector，已移除静态能力查询。
- `lib.rs` 的 WindowEvent fallback 明确排除 Android/iOS；iOS 单主窗口恢复由 `infra/ios_window.rs` 处理，不重启 Rust bootstrap。
- Rust 保存 `phase/nativeSequence/snapshot` 和独立的 transition epoch；首次原生快照前 `lifecycle_snapshot` 为 `None`，前端不会据 legacy bool 的初值启动恢复。
- Vue 的 `document.hidden` 仍是 UI visibility hint；实际 active/inactive/background 由 Rust 原生快照提供，网络事件只提示既有恢复 owner 可以重试。
- 以上是源码接入事实，G1 尚未执行；Chat/Sync 领域收尾与原生后台资源绑定仍属于 Phase 3/5。

当前 native DTO 为：

```json
{
  "phase": "active | inactive | background",
  "nativeSequence": 42,
  "snapshot": false
}
```

首期沿用单 Scene 产品形态。沿 Tauri/tao 的启动代码核对 Scene manifest、delegate 和通知来源；Swift 聚合 app phase，Rust 使用现有 `lifecycle_controller` 的 transition epoch、单锁和后台区间 cancellation token。Scene 接入随选定 SDK 和模板检查，版本升级单独评估对 Android 的影响。

## Continued-task 候选的生命周期状态机

以下状态表和 Chat 的 active-task 判断描述 continued-task 这一候选路径。P5-1 若选择其他可成立的 SSE 保活资源，必须同时更新退后台继续/收尾条件及对应 owner，不能因没有 continued task 就抢先取消仍满足选定运行条件的 SSE。

```text
ACTIVE
  -> INACTIVE_PREPARED
  -> BACKGROUND_CONTINUED(activeTask) 或 BACKGROUND_CLOSING(epoch, deadline)
  -> SUSPEND_SAFE（task terminal 后）
  -> FOREGROUND_RECONCILING
  -> ACTIVE
```

- `INACTIVE_PREPARED`：系统弹窗、控制中心或暂时失焦也会发生；暂停 UI 动画，保留业务请求，准备单例 closing assertion。
- `BACKGROUND_CONTINUED`：保留已激活 task 对应的 Rust attempt，关闭其他领域的后台循环；
- `BACKGROUND_CLOSING`：缺少活动 continued task 或系统结束任务时，各领域在 deadline 内返回 receipt 并释放 assertion；
- `SUSPEND_SAFE`：领域任务已落终态，连接、文件和 native token 已按 owner 释放。
- `FOREGROUND_RECONCILING`：先按 native sequence 对账，再按实际网络结果与 settings 恢复持久连接。

`beginBackgroundTask` 用于 cancel/finalize、join/flush 的有界收尾。原生 owner 配对 begin/end；deadline 与 expiration 进入同一终态路径。continued task 的运行资源由独立 task binding 持有。

## 分领域策略

### Chat

可复用：

- UUID attempt + `CancellationToken`；
- ABA-safe `ActiveRequestLease`；
- 非 Android `reqwest` SSE 前台路径。

必须补齐：

- lifecycle 级 `cancel_all(reason)`；
- first-writer-wins `CancellationCause`，至少区分 user、background、system-task-ended、transport；
- settle receipt/Notify，让 lifecycle 可以有界等待 terminal；
- attempt ID 与 native work lease/task ID exact-once 绑定；
- lease acquire 失败作为显式结果进入前台回退。

当前 partial content 主要在内存 buffer/channel，终态才提交数据库。正常取消应让该 owner 提交已有内容与原因；进程终止后按实际持久化的 pending/attempt identity 对账。在 continued-task 候选路径下，缺少活动 task 时 background 进入 `interrupted_by_background`；有活动 task 时延续同一 SSE，system end 则记录对应原因。最终采用的保活方式及其失效条件由 P5-1/P5-2 接回同一 owner，Retry 仍由用户发起。

### 手动 Sync

当前 `SyncState` 已有 session ID、CancellationToken、JoinHandle、child drain 和 generation 失效，是可复用的正确 owner。缺口是 lifecycle 没调用它、loopback 校验只认 Android。

首版规则：

- background 调内部 `stop_sync_inner(reason, deadline)`；
- 先 invalidate generation，再 cancel children、drain DB write queue、join；
- 保存 terminal receipt；
- 回前台保留 terminal，下一次同步由用户主动 `start_manual_sync` 发起。

### VCP Log / Info

现有 Android 策略是 Log 10 分钟 linger、Distributed 5 分钟。iOS background 策略单独由 lifecycle owner 选择：

- Log/Info 立即停止 heartbeat、flush 有界缓存并关闭；
- 缓存按固定预算 flush；
- 回前台按 settings 和真实 endpoint probe 重连。

### Distributed

完整 Distributed/设备工具已获批兼容，Phase 3 的 P3-4/P3-5 接入；当前目录和传输 owner 已存在，iOS 工具 adapter 尚未完成：

- 复用 client、registry、用户逐工具授权与 telemetry owner，按真实工具实现和返回字段呈现结果；不恢复统一静态能力表或重复平台门禁；
- 前台接入设备/网络/传感器查询，缺少 API、未授权或暂不可读的工具/字段明确报告，不让一个缺失值使整个节点失效；
- iOS 不照搬 Android 的五分钟 linger 和前台服务。Phase 3 先闭合 stop/join 与前台重连，Phase 5 再定义设备采样和连接的后台策略。

### Updater 与维护

- APK update check/download/install 由共享 Vue 的 Android 分支启动；iOS 更新入口保留自签安装说明；
- 30 秒 maintenance、24 小时清理和自动 refresh 在 iOS background 暂停；
- coordinator 仅保留绑定当前用户 continued job 的任务，回前台后按原调度意图恢复。

## Continued processing 实施清单

以下工作依赖 DTO、attempt owner 和 API 声明，可在源码开发阶段完整实施：

1. 用户明确动作创建稳定 job/attempt identity；
2. task identifier 采用最终 Bundle ID 与 attempt suffix，plist 的 permitted identifier 同步处理，签名改写见 06；
3. iOS 26 availability 分支接入当前 `submit(_:)`；新 SDK API 按声明逐项适配；
4. `SUBMITTED` 与 `ACTIVATED` 分开；优先 `.fail` 取得即时拒绝，handler 与前台 fallback 竞争同一启动权，迟到 handler 检查 attempt generation；
5. 以本节进度 DTO 驱动 Swift 映射；总量未知分支保留累计数量和明确终态；
6. expiration 与系统 UI 取消归为同一 system end 原因；
7. 正常 terminal、App 内取消、system end 和 Rust error 由一个 compare-and-complete owner exact-once 收敛；
8. 进程重启按数据库中已有记录对账；
9. 原生事件经 Channel 进入 Rust，桥接任务接收迟到响应的处理沿用 01 的生存期规则。

## 网络、LAN、ATS 与 loopback

- Rust 主网络是 `reqwest/rustls` 和 `tokio-tungstenite/rustls`，在 transport owner 实施 scheme/TLS/证书 policy；URL Loading System 使用对应 ATS 配置。
- 默认只允许 HTTPS/WSS；HTTP/WS 仅对用户显式配置的受信 LAN，并给出清晰警告。
- 按 [Apple Local Network 说明](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)加入 `NSLocalNetworkUsageDescription`，拒绝/网络错误归约为可恢复状态，用户从设置返回后重新 probe；
- `NWPathMonitor.satisfied` 触发一次 endpoint probe，连接状态以领域实际请求结果更新。
- Sync 必须把 iOS 当 mobile，拒绝电脑端 `localhost/127.0.0.0/8/::1`。
- 大附件的 WebView XHR → Rust `127.0.0.1` 上传沿现有 token、CORS、长度与 deadline 路径补齐取消和生命周期收尾，见 05；
- SSE/WebSocket 继续使用 Rust owner；未来系统接管的文件传输可单独评估 background URLSession。

- sequence/乱序/重复生命周期；
- inactive 保留业务、background 按 active task 分支继续或收尾；
