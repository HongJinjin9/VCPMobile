## 2026-10-07 总体路线

```text
Phase 0  固定输入、恢复产品决定、目标源码审计
Phase 1  平台能力、cfg/ACL、目录与 DTO
Phase 2  Swift 插件、Channel、生命周期
Phase 3  核心 Chat/Diary/Settings/SQLite/Sync
Phase 4  原生文件/图片 P0 与 WebKit 交互
Phase 5  尽力后台、真实进度与单次终态
Phase 6  GitHub Actions 阶段验收与用户自签产物
```

这是依赖顺序。Phase 4 在目录/DTO 确定后可与核心业务并行，Phase 5 在 attempt/terminal 定义完成后即可实现；Phase 6 的工程与脚本从 Phase 2 起准备。日常完成条件按 07 的源码覆盖、分支演算、缺陷闭环及本地辅助检查落实。

Apple 构建固定在 GitHub Actions 阶段性手动执行：Phase 2 收束后进行 G1 插件/生命周期接入验收，Phase 3–5 集成后随 Phase 6 进行 G2 release 构建与打包验收。iPhone/iPad 的输入差异直接进入源码审计清单；默认验收对象为 device archive，具体步骤见 07。

## Phase 1：平台能力与共享契约

2026-10-08 已完成，文件级实施见 [阶段子规划](./phase-1/00-阶段子规划.md)，实际验证与剩余阶段任务见 [验收与 Phase 2 交接](./phase-1/07-验收与Phase2交接.md)。Apple 原生接入仍属于 Phase 2；以下保留阶段目标。

目标：

- 建立 typed `PlatformCapabilities`，分离 support/implementation/authorization/runtime；
- 前端启动先读取 capability，再挂 PermissionGate、Updater、语音、Root/CLI/Distributed 等入口；
- cfg 拆为 Android/iOS/host-test；
- iOS 返回 adapter 的真实结果，host 数据留在开发分支；
- Android/iOS capability 分文件，portal 最小授权；
- Android 专属命令归相应平台 owner，完整设备工具按既定范围延期；
- 将附件 data/cache/staging 目录语义平台化；
- 把 lifecycle DTO 升级为 phase + native sequence + snapshot。

完成条件：

- Android 消费者仍连接原有实现与数据目录；
- capability、ACL、Rust/TS DTO 和 UI 消费一致；
- 每条返回结果都对应实际状态/副作用或明确错误；
- `pnpm check` 与针对字段、取消、路径的必要检查通过。

下一阶段输入是确定的 DTO、命令映射、目录接口和状态所有者。

## Phase 3：前台核心

实现与源码审计路径：

- iPhone/iPad 共用启动链到 READY；
- SQLite 初始化、写入、重启持久化；
- Settings、Diary；
- 前台 Chat 成功/取消/错误 terminal；
- 手动 Sync start/stop/join；
- native lifecycle active/inactive/background 基础 round-trip；
- 根返回使用现有 modal/page/session owner；
- 各功能入口与能力表一致。

生命周期策略：

- 先完成前台执行与有界 cancel/stop/join/flush；
- 回前台恢复持久连接，Chat/手动 Sync 由用户再次发起；
- 预留 Phase 5 的 active task 判断，尽力后台接入同一 owner。

完成条件：

- 每条调用有明确结果、取消原因与数据提交点；
- 领域测试覆盖旧 generation 回调、取消后的写入与重复终态；
- 前台路径逐条记录入口、输入、状态迁移、结果消费和资源释放，正常与异常分支均有对应审计结论。

## Phase 4：文件、图片与 WebKit 交互

施工顺序：

1. 核对 HTML IPC、loopback、native staging 三条入口到 CAS 的调用；
2. 原生 Files Document Picker/security-scoped copy；
3. PHPicker 临时文件复制、ImageIO 大图/HEIC，以及 `convert_local_image_for_multimodal` 的 iOS 输出路径/MIME/预算与清理；
4. 上传 abort、generation、staging 清理和错误返回；
5. safe area、visualViewport/Swift keyboard bridge；
6. Mermaid/KaTeX/raw HTML/Canvas/长会话 fixtures；
7. iPad presentation、焦点/返回、命中区与输入字号。

相机、录音、保存相册、incoming/outgoing share、系统通知/APNs、视频抽帧沿用既定延期范围；入口按 capability 处理。

完成条件：

- staging containment、大小、hash、TTL 与取消；
- 大文件以路径/ticket 交接，像素缓冲、并发和副本预算明确；
- portrait/landscape、iPhone/iPad 输入与弹层具有一致单位和唯一 Insets 来源；
- 强渲染 fixture 对应实际 DOM/样式/交互，保留现有消息能力。

## Phase 5：尽力后台

目标：

- iOS 26 availability、request/handler/expiration/completion 接入；
- attemptId 与 taskId 绑定，提交拒绝时采用前台常亮；
- Rust 真实累计字符/字节/可选 token → Swift Progress 与系统标题；
- 由 active task 决定 background 继续或收尾，其他连接/维护循环按领域关闭；
- 正常完成、用户取消、system end 和 transport error 共享单次 terminal。

完成条件：

- 04 的状态表和每种分支都有对应生产实现；
- 注册/提交/激活顺序明确，迟到 handler 按 generation 归属；
- Progress 已知/未知总量分支有具体映射，真实事件驱动计数；
- 取消、expiration、终态竞争有可复现事件序列；
- runtime Bundle ID 与 plist 任务前缀一致。

## Phase 6：GitHub Actions 集中验收与用户产物

前序阶段完成源码审计和脚本准备后，手动触发 G2，在 GitHub Actions macOS runner 集中执行：

- 固定 Xcode/SDK 并生成 Apple 工程；
- Rust/Swift release 构建、链接、Scene 配置、native Channel 注册与资源装配检查；
- device archive 的 Mach-O、动态依赖、plist、资源检查；
- `.app.zip` 与通过结构检查的 `.unsigned.ipa`，附 manifest/SHA-256 和用户签名说明。

复用本次 release archive 完成检查和打包。确有具体启动/桥接问题需要运行诊断时，按 07 手动启用 Actions 内的单项 Simulator 诊断。

产物完成条件：

- D15/D18 范围实现完整，具体缺陷按影响路径处理；
- 交付 archive 的平台标记为 device，打包结构符合 06 的签名输入设计；
- 最终 Bundle ID 改写步骤覆盖 plist 与 entitlement；
- 源码审计覆盖记录、G2 构建诊断和包检查结果指向对应 commit 与输入；
- 发布时按仓库规则取得该动作授权，iOS 资产附加与 Android APK 独立处理。

D16 的静态内存/资源预算贯穿实现。后台调度、授权与 provider 事件按 07 的分支矩阵演算，已发现问题在对应 owner 闭环；用户签名说明随产物交付。

## 问题处理与推进规则

- 找到类型、符号或调用错误后修对应实现，并记录受影响的目标分支；
- 缺少声明时先查锁定源码/API/模板，列出精确待办，继续其他独立工作；
- 日常通过源码审计推进技术依赖；GitHub Actions 只在阶段验收时手动运行，诊断修复后集中复验；
- Android 回归影响按实际消费者定位，平台适配保持共享领域 owner；
- 产品范围变化回到 09 的决定记录，以用户选择更新任务；
- 各阶段记录实际完成项、剩余问题与下一具体动作。
