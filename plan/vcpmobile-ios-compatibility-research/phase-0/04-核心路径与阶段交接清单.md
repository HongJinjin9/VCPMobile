## 3. Phase 1 的可执行起点与交付界面

1. **能力单一来源。** 从 Rust 进程级平台信息与实际 adapter 出发，固定 `support / implementation / authorization / runtime` 的 typed 结果；前端由启动 owner 获取后交给现有消费者。不要新增纯转发层或在各 Feature 重复判断 UA。能力读取失败要有明确错误/重试状态，不能把未知归为已授权成功。
2. **一起封闭调用和入口。** 第一批覆盖启动权限链、APK updater 全链、Root/CLI/Distributed、系统通知、相机/语音/分享入口；同时维护 Rust cfg、插件 permission 与 iOS capability 文件。只改 `v-if` 不能完成后台调用隔离。
3. **先固定跨层形状。** lifecycle phase/native sequence/snapshot，native 文件 path/ticket/MIME/size，attempt/task/cancellation cause 与收尾结果由当前 owner 承接。具体 Swift API 在 Phase 2/4/5 实现，Phase 1 不返回虚构成功 DTO。
4. **目录逐消费者迁移。** 用现有 file/persistence/settings owner 的实际调用确认 data/support、cache、staging；Android 既有路径保持。每个 iOS 外部路径进入受控复制/登记流程，不让 picker 返回值直接成为长期 CAS 路径。
5. **交付 Phase 2 的确定输入。** 命令分类与授权集合、平台 cfg 边界、DTO、目录接口、平台启动顺序和 owner 表应可逐项对照。涉及前端/跨层/核心变更时执行 `pnpm check`，并按受影响路径做必要检查；这些检查不替代 Apple 构建。

Phase 1 文档在开始实施前根据这批交接内容展开具体文件修改、分支演算与完成记录；Phase 0 不提前写成这些目标已经实现。

## 4. 交互、系统与交付的 Magi 裁决

| 争议 | Melchior：系统约束 | Balthasar：交互约束 | Casper：交付约束 | 本次结论 |
|---|---|---|---|---|
| 仅隐藏 Android 页面是否足够 | composable 初始化、Rust 服务与 ACL 仍可触发副作用 | 用户不能看到无作用按钮、错误权限引导或 Android 后台警告 | 避免搭建无消费者的通用路由框架 | 在现有能力与生命周期 owner 同时控制可达调用和显示；集中列出消费者，一批闭合 |
| 先做 HTML 附件是否可结束首版 | 三入口可共享 CAS，但 native staging 有独立资源生命周期 | Files/照片选择与大图属于真实手机输入路径 | HTML 子路径能先联调，不能用中间里程碑替代 D18 | Phase 4 保留 Files/PHPicker/ImageIO P0；分批实现并共享登记 owner |
| 前台 Chat 是否可以替代后台范围 | 需要同一 attempt 与唯一 terminal；不能用第二条请求续跑 | 拒绝/系统结束后说明状态，由用户重试 | 先完成 bounded 收尾，后接 continued task，避免阻塞前台核心开发 | Phase 3 前台里程碑，Phase 5 完成 D2/D15；任务拒绝走前台常亮，不改变首产物目标 |
| 是否为 iOS 重新建设页面/返回栈 | 多 owner 容易产生状态分叉与重复关闭 | 保留高密度 UI，适配选择、焦点、iPad presentation 与根返回 | 在同一组件树增加平台/窗口策略 | 复用现有 overlay/page/modal/session；根部保持应用，Insets 明确单位，不复制 iPad Store |
| 是否增加实机/常驻 Simulator 门禁 | 静态推导和构建结果各有证据范围 | iPhone/iPad 输入条件仍应明确并逐项演算 | 用户已经固定源码+阶段 Actions 的工作方式 | 不建立 iOS 实机体系，不新增产品门禁；按 07 记录源码覆盖和 G1/G2 结果，具体运行疑难才在 Actions 手动选择单项 Simulator 诊断 |

这些裁决落实既定用户决定，并非另起一组 N 编号重写 D1–D19。未知总量的系统 `Progress` 映射属于 Phase 5 具体 API 问题；应继续查明声明与状态分支，同时推进独立路径，不改成合成业务进度或删除尽力后台。

## 5. Phase 0 完成与 G1/G2 的界限

| 时点 | 应完成的工作 | 不归该时点的工作 |
|---|---|---|
| Phase 0 收束 | 记录 commit/任务工作树；恢复 D1–D19；重抽命令/permission/selector/消费者；审计 target cfg、锁定依赖/FFI/build script；确定或逐符号列明 minimum/模板/资源/签名输入剩余项；为问题安排 owner 与阶段 | 不声称 iOS 已可运行，不运行 Apple 构建，不新增实机/性能门禁，不自动触发 CI 或发布 |
| Phase 1–2 完成后 G1 | 用户手动触发独立 iOS Actions，device debug archive 集中检查 cfg/ACL、DTO、Swift 插件/Channel/生命周期的编译、链接与资源装配；诊断回到具体源码闭环 | 不逐次修改触发 Apple 构建，不把 debug archive 当首产物 release；默认不启动 Simulator |
| Phase 3–5 集成后、随 Phase 6 执行 G2 | 手动 Actions device release archive；检查 Mach-O、动态依赖、plist、资源和 bundle；复用成功 archive 生成 `.app.zip`、经结构检查的 `.unsigned.ipa`、manifest/SHA-256 与自签说明 | 不另造 iOS 设备测试体系，不自动正式签名，不因产物准备完成推断获得 push/Release 发布授权 |

Phase 0 “完成”表示输入、源码发现与后续动作可以支持 Phase 1 开工。各类待办按实际依赖推进；某个 Apple API 声明待核对，不阻止与其无关的能力、目录与入口隔离工作。必须保留“未实现”“未构建”的准确状态，不能把 Windows host 静态检查改写为 Apple 执行证据。

## 6. 根规范的最小同步建议

- 根 `AGENTS.md` 的平台说明应区分“当前 Android 生产目标”与“已经授权推进的原生 iPhone/iPad 兼容目标”，移除禁止 iOS 的冲突；保留桌面、Android TV 和其他 Android ABI 的排除，不把 host fallback 扩成产品入口。把 iOS 工作方式指向本研究的 D14/07/08，明确无 iOS 实机体系且 Apple 构建只在阶段性 Actions。

- `src/AGENTS.md` 的“当前 Android 窗口宽度”可最小扩为当前移动窗口宽度并说明 iOS 正在分期接入；不修改现有组件、Store 与覆盖层所有权规则。插件局部文档在 Phase 2 Swift 子树实际落地时更新目录与调用链，Phase 0 不把未存在的 Swift 路径写成实现事实。
