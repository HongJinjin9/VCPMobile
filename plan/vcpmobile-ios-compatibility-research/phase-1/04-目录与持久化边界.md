# Phase 1：目录与持久化边界

> 2026-10-08；实施基线 `489b3341`。本文按当前生产调用链记录目录 owner、平台分支与交接；iOS 路径为锁定依赖的源码语义，尚未取得 Apple 运行结果。

2026-10-09 校准：目录与 CAS owner 继续复用；下列依赖版本和执行值保留 Phase 1 基线，不重记为 Tauri 2.12.1 的新结果。统一平台能力表已删除，功能呈现使用同步平台身份；文件/媒体/双向分享/WebKit 的活动任务见 Phase 4。

## 1. 目录事实与本轮选择

目录解析继续由 [`file_manager.rs`](../../../src-tauri/src/vcp_modules/infra/file_manager.rs) 提供，不新增全局路径状态或数据迁移程序。解析函数不创建文件；具体读写、创建与回收仍归原来的业务 owner。

| 语义与解析入口 | Android 保留的来源 | iOS 本阶段来源 | 实际消费者 |
|---|---|---|---|
| 私有支持目录 `get_support_root_dir` | `app_config_dir()`，锁定 Tauri 的 Kotlin 实现返回 `activity.dataDir` | `app_data_dir()`，`Library/Application Support/<实际 identifier>` | `db_manager::init_db` 的 `vcp_avatar.db`；受支持平台的文件打开范围校验 |
| 附件持久根 `get_data_root_dir` | `document_dir()` 的父目录，即现有 external files 根 | 与支持目录相同，不对 Documents 执行 `pop()` | 附件与缩略图根的派生 |
| CAS `get_attachments_root_dir` | 现有 external files 下 `attachments/` | 支持目录下 `attachments/` | 小文件 IPC、原生 staging 登记、HTTP 上传、CAS 解析及维护 GC |
| 已登记缩略图 `get_thumbnails_root_dir` | 现有 external files 下 `thumbnails/` | 支持目录下 `thumbnails/` | SQLite `thumbnail_path`、附件展示及维护 GC |
| 可丢弃缓存 `get_cache_root_dir` | `app_cache_dir()`，Kotlin 返回 `activity.cacheDir` | `app_cache_dir()`，`Library/Caches/<实际 identifier>` | 文件打开范围、暂存目录、冷启动清理、维护目录 |
| 上传暂存 `get_upload_staging_dir` | 原有 `app_cache_dir()/uploads` | 缓存目录下 `uploads/` | `register_local_file`、`high_speed_channel::prepare_vcp_upload`、`clear_upload_cache` |
| 可重算多模态缓存 `get_multimodal_cache_dir` | 原 external files 下 `multimodal_cache/` | 缓存目录下 `multimodal_cache/` | 音频/视频抽取缓存命中与写入、容量淘汰和附件 GC |

**Android 路径不迁移。** 旧 `db_manager` 注释曾将私有配置目录描述为 `.../files`；实际锁定依赖返回的是 `activity.dataDir`。本轮保留原 API，仅修正说明，不按错误注释搬数据库。附件 external files 与 SQLite 私有根原本不同，不能合并为一个 Android 数据根。

**host 只用于开发。** `get_data_root_dir` 保留原 `document_dir().pop()` 布局，支持目录继续用 `app_config_dir()`；两者置于明确的非 Android、非 iOS 分支。本阶段不迁移开发文件，也不将这个分支当作 iOS 实现。

**缩略图保持持久。** 当前 SQLite 存储完整 `thumbnail_path`，Rust 的 `generate_thumbnail` 尚未提供平台通用重建能力；将缩略图直接移到可被系统丢弃的缓存目录会破坏现有消费者。只有已有缓存 miss 后重新计算路径的多模态 JSON 在 iOS 进入缓存目录。

## 2. 锁定 API 的来源

本轮读取本地 Cargo 锁定源码，定位方式以 crate 与相对路径表示：

- `tauri@2.11.5/src/path/android.rs`：`app_config_dir` → `getConfigDir`，`app_data_dir` → `getDataDir`，`app_cache_dir` → `getCacheDir`，`document_dir` → `getDocumentDir`。
- `tauri@2.11.5/mobile/android/src/main/java/app/tauri/PathPlugin.kt`：前两者返回 `activity.dataDir`；缓存返回 `activity.cacheDir`；Documents 返回 `getExternalFilesDir(Environment.DIRECTORY_DOCUMENTS)`。
- `tauri@2.11.5/src/path/desktop.rs`：非 Android 路径实现的 `app_data_dir`、`app_config_dir`、`app_cache_dir` 分别在 `dirs` 结果后追加 `config.identifier`。文件名为 `desktop.rs` 不代表它不被 iOS 使用。
- `dirs@6.0.0/src/lib.rs` 显式将 iOS 与 macOS 映射到 `mac.rs`；后者的 data/config 为 home 下 `Library/Application Support`，cache 为 `Library/Caches`。

因此 iOS 路径使用实际 Tauri identifier，不硬编码 `com.vcp.avatar` 或设备容器 UUID。G1/G2 可以核对编译目标和工程 identifier，但不能据此宣称观察了设备进程的实际路径；上述目录判断仍是相应依赖基线的源码语义。

## 3. 持久化消费者与未改动的所有权

- [`db_manager.rs`](../../../src-tauri/src/vcp_modules/persistence/db_manager.rs) 从支持目录创建/打开 `vcp_avatar.db`，后续 WAL/SHM、事务、损坏归档和恢复仍由原数据库 owner 管理。路径解析失败向上传播，未增加自动迁移或重建数据库的分支。
- `settings_manager.rs` 通过 `DbState` 存取 SQLite，没有需要迁移的独立 `settings.json`。本轮不复制 Settings 状态或改变其存储协议。
- `diary_service.rs` 通过 HTTP 访问服务端日记，只借助 `DbState`/`SettingsState` 读取连接设置；当前没有独立本地日记目录，不能因为规划中出现 Diary 而新建磁盘 owner。
- `boot_trace.rs` 已用 `app_data_dir()` 保存有界启动记录；Sync 日志已用 `app_log_dir()/sync_logs`，无需迁移。CLI 和 Distributed 的私有状态使用各自 `app_config_dir()`；实际运行由原领域/原生实现决定，不再依赖统一平台能力表。
- 音频/视频缓存、附件维护 GC 等下游已经通过 file manager 解析目录，本轮修改解析语义即可到达真实消费者，不逐个复制 iOS 路径分支。

## 4. staging 输入、异常与释放

三条现有附件链继续汇入 Rust CAS/SQLite。小文件 IPC 不需要外部路径；[`high_speed_channel.rs`](../../../src-tauri/src/vcp_modules/infra/high_speed_channel.rs) 的 HTTP 上传与原生 `register_local_file` 共享 `get_upload_staging_dir`。Android 原生仍在 `context.cacheDir/uploads` 复制，路径与现有 Tauri API 相同。

`register_local_file` 的 canonical 与直接文件检查集中为 `canonical_staged_file`：主附件必须是 `uploads` 的直接普通文件，缩略图必须是 `uploads/thumbnails` 的直接普通文件。目录本身、嵌套主附件、父级逃逸和解析后越界路径均拒绝。原有 512 MiB 上限、同一句柄元数据/流式读取、64 KiB 堆缓冲、大小一致性、Rust SHA-256 与原生 hash 提示校验继续保留；原生路径或 hash 不能绕过 CAS 登记。

| 分支 | 现有资源归属与本轮保持的结果 |
|---|---|
| 目录解析/创建、文件打开失败 | 返回实际错误，不伪造空路径或成功附件 |
| 越界、非直接文件、大小/hash 不符 | 登记失败，不将文件送入长期 CAS |
| CAS 命中或跨目录复制后登记成功 | 原导入 owner 删除 staging 源文件；删除失败记录警告，已经完成的附件登记仍成功 |
| rename 后 SQLite 登记失败 | 保留完整 CAS，交给重试或维护 GC；不与并发同 hash 登记竞争删除 |
| 主附件成功、缩略图失败 | 保留主附件结果，缩略图失败按既有路径记录；不回滚已登记主文件 |
| HTTP 错误/超时 | 原连接 owner 删除本次临时文件；保留原 200 MiB 上传上限与连接/闲置期限 |
| 崩溃或强杀遗留 | 原 `lib.rs` setup 在 bootstrap 前调用 `clear_upload_cache`；同一目录函数解析 uploads，再按原启动清理时点处理 |

这不是完整的原生导入取消协议。当前 Vue 删除 staged 条目并不等于取消所有传输或释放 picker 资源；ticket/generation、迟到响应与原生 provider 资源仍归 Phase 4 施工。本轮没有新增 picker 或伪造原生导入 DTO。

## 5. WebView 维护与文件预览边界

[`maintenance_manager.rs`](../../../src-tauri/src/vcp_modules/infra/maintenance_manager.rs) 的 `WebView/Default/HTTP Cache` 和 `code_cache` 属现有 Chromium 路径，不能作为 iOS WebKit 的清理实现。

- iOS `clear_webview_cache` 返回带 `not_implemented` 前缀的中文未实现错误；Android 及既有 host 开发分支保留原清理位置。
- `reconstruct_system_cache` 在 iOS 只执行现有 SQLite 增量整理/索引优化，并返回数据库维护结果；V8 目录清理在编译条件外排除。
- SQLite 维护失败现向调用者返回错误，消除旧实现忽略错误后仍报告完成的行为。Android 的维护动作和目录保持。
- app 层 `open_file` 对 iOS 返回 `not_implemented` 与未接入说明；Android 保持 `open_file_native`，host 才保留 opener。Phase 4 接入真实预览后更新该分支与现有消费者，不恢复 capability 字段。

## 6. 交接与验证

Phase 2/4 必须注意：Swift 的系统 Caches 路径不能假定等同于 Tauri `app_cache_dir()`，后者追加了实际 identifier。后续原生文件/照片复制应使用 Rust 目录 owner 指定的受控目标和导入 identity，再回到同一 Rust containment/hash/CAS 入口；不能让外部 provider URL、security-scoped URL 或 PHPicker 临时 URL 成为长期附件路径。

| 检查 | 本子任务执行状态 |
|---|---|
| 四个改动文件的 Rust 格式与 diff 空白检查 | `rustfmt --check --edition 2021` 与 `git diff --check` 通过 |
| file manager 路径/CAS 定向回归 | `cargo test --locked --lib security_boundary_tests`：9 passed；Windows 不执行 `cfg(unix)` 的 symlink 专属分支 |
| HTTP 上传定向回归 | `cargo test --locked --lib high_speed_channel`：5 passed |
| 项目 `pnpm check` | 主任务统一执行，见阶段验收记录 |
| Android Rust 目标检查 | `cargo check --locked --offline --target aarch64-linux-android`：通过，退出码 0，1 分 01 秒；环境来源见下节 |
| APK 构建、iOS 编译/运行 | 本目录子任务未执行，不由 Rust 目标检查替代 |

Casper 裁决：复用实际目录 owner 和现有导入/持久化链，不建立统一路径注册服务，不迁移 Android 或 host 既有文件。后续阶段根据真实原生实现补充所需契约，不能以 Phase 1 目录函数已存在宣称 iOS picker、预览或资源取消已完成。

## 7. Android Rust 目标检查环境记录

在主任务 host 检查释放 Cargo 后，复用现有 `src-tauri/target` 执行一次 Android Rust 检查。先读取 `tests/AGENTS.md`、Android Debug 脚本和已存在的 SDK/NDK 配置；没有调用 Debug 工具的设备入口。

| 输入 | 本轮来源与有效值 |
|---|---|
| Rust target | `rust-toolchain.toml` 声明 `aarch64-linux-android`；`rustup target list --installed` 确认本机已安装，无下载 |
| SDK | 读取未入库的 `src-tauri/gen/android/local.properties`，本机解析为 `D:\Android\Sdk` |
| NDK | 已安装 SDK 下 `ndk/29.0.14206865/source.properties`：`Pkg.Revision = 29.0.14206865`、r29 |
| Android API | 当前 `src-tauri/gen/android/app/build.gradle.kts` 的 `minSdk = 26` |
| C/C++ 编译器 | NDK `toolchains/llvm/prebuilt/windows-x86_64/bin/aarch64-linux-android26-clang.cmd` 与 `aarch64-linux-android26-clang++.cmd`，均先确认存在 |
| archive / linker | 同一 NDK 的 `llvm-ar.exe`；Rust 目标 linker 指向上述 API 26 clang |
| 子进程环境 | `ANDROID_HOME`、`ANDROID_SDK_ROOT` 指向 SDK；`NDK_HOME` 指向 NDK；设置 `CC_aarch64_linux_android`、`CXX_aarch64_linux_android`、`AR_aarch64_linux_android`、`CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER`，不写持久环境或 Cargo 配置 |
| SQLite 输入 | 已锁定 `libsqlite3-sys 0.37.0` 的 bundled build 在 `android_target()` 分支添加 `SQLITE_TEMP_STORE=3`；未添加额外 SQLite flags。已有 Android build 输出中的 CC/AR 与本轮选择一致 |
| 工程范围 | 不设置 `TAURI_ANDROID_PROJECT_PATH`，不启动 Gradle、APK 构建或设备操作；未读取 CI/Release workflow、改动 build 源或锁文件 |

执行目录为 `src-tauri/`，命令为 `cargo check --locked --offline --target aarch64-linux-android`。退出码 0，完成用时 1 分 01 秒。执行时有一条 `set_app_foreground_state_for_epoch` 在 Android 无消费者的 dead-code 警告；收尾已将该唯一 host WindowEvent 入口和 re-export 限定到 host cfg，最终 host 静态检查无警告。该目标检查没有编译错误。

此结果验证实际 Android Rust 条件分支与依赖类型检查，允许复用此前的原生 archive。它不代表重新编译全部 C/Kotlin、完成链接、生成 APK 或取得设备执行证据；也不替代后续 Apple G1/G2。
