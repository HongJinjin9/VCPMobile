# Android 与 iOS 跨平台开发规范

> 适用范围：共享 Vue/Rust、Tauri IPC、Android Kotlin/JNI、iOS Swift 与平台工程配置。2026-10-09 建立。
> 功能目标以用户最新决定为准，当前实现以生产代码为准。本规范规定后续开发的组织方式；其中待落地的呈现和错误处理约定不代表现有代码已经具备。

跨平台功能沿同一条业务链开发：Vue 表达用户意图，Rust 领域模块拥有业务状态，平台适配层执行系统操作。编译目标决定哪些原生代码参与构建，能力事实决定哪些操作可以尝试，产品决定控制入口和说明，操作结果决定最终反馈。

本规范与 [移动端 UI 兼容性规范](./MOBILE_UI_COMPATIBILITY.md) 配合使用：后者管理窗口、布局、CSS、Insets 和触控；本文件管理平台分支、能力、权限、命令及提示。Android 原生细节继续见 [Android 插件管理规范](./ANDROID_PLUGIN_MANAGEMENT.md)。

## 1. 先确定差异属于哪一层

| 要回答的问题 | 所属层与依据 | 例子 |
|---|---|---|
| 这段代码、依赖能否进入目标产物 | Rust `#[cfg]`、Cargo target 依赖、原生 target；必要时前端构建裁剪 | JNI 仅编入 Android，UIKit 仅编入 iOS |
| 当前安装版本是否有对应实现 | Rust 平台能力及原生观测，Vue 消费能力快照 | 已批准接入相机，但 adapter 尚未完成 |
| 当前系统版本和设备能否执行 | 原生 API availability 与真实运行条件 | 某后台 API 在较旧 iOS 上不可用 |
| 用户是否授权本次访问 | 对应原生权限 owner | 相机被拒绝、照片访问范围受限 |
| 入口显示什么、点击做什么 | 用户功能决定与领域 UI | iOS 更新入口保留，点击说明 App 外自签安装 |
| 已执行操作是否成功 | 真实返回值、事件与业务终态 | 导出完成、用户取消、存储不足 |

这些判断不能相互替代。`isIos` 不表示某项 iOS 功能已实现；`isImplemented` 不表示已获授权；按钮可见不授权原生副作用；编译通过不保证系统会持续给后台任务运行时间。

## 2. 编译目标与代码隔离

### 2.1 Rust 与 Cargo

平台专用的 import、类型、实现和依赖必须落在相同的目标边界。使用准确的 `target_os`，明确区分 Android、iOS 与 host 开发分支：

```rust
#[cfg(target_os = "android")]
mod android;

#[cfg(target_os = "ios")]
mod ios;

#[cfg(not(any(target_os = "android", target_os = "ios")))]
mod host;
```

这是模块隔离形式的示例，不要求把所有现有小分支拆成三个文件。少量差异可以留在函数内部；当平台资源、清理流程或类型体系已经独立时，再按领域拆分适配模块。共享请求解析、持久化和业务终态留在原领域 owner，不复制成两份业务实现。

- `#[cfg(not(target_os = "android"))]` 包含 iOS，不能用它承载 host 假实现。只有各目标语义确实相同的共享代码才使用宽条件。
- `cfg!(...)` 只生成布尔值，不移除分支；平台上不存在的类型或 API 需要 `#[cfg]` 隔离，不能依靠 `if cfg!(...)` 绕过编译。见 [Rust cfg 文档](https://doc.rust-lang.org/stable/core/macro.cfg.html)。
- 原生依赖放入对应的 `[target.'cfg(target_os = "android")'.dependencies]` 或 iOS 段；Cargo feature 用于可选能力，不另建能与目标 OS 冲突的 `ios=true` 产品开关。见 [Cargo 平台依赖](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#platform-specific-dependencies)。
- `build.rs` 自身运行于构建主机；需要选择产品目标时读取 Cargo 提供的目标环境信息，不能以构建脚本自身的 `cfg!(target_os)` 判断正在构建的手机平台。
- host scaffold 和 fixture 不建立桌面产品能力。iOS 未实现返回真实不可用结果，不返回模拟电量、空成功文件路径或无副作用的 `Ok(())`。

### 2.2 Kotlin 与 Swift

Kotlin、JNI 与 Android 组件留在 Android target；Swift、Apple framework 与 Apple 工程声明留在 iOS target。Swift 的条件编译和运行时 `#available` 分工不同：SDK 能编译某符号，不代表 minimum system version 覆盖的全部设备都能调用。Android 新 API 同样要按实际版本条件处理。

系统对象的生命周期归原生适配层，Chat/Sync/SQLite/CAS 等业务生命周期归 Rust。原生 UI 必须在对应 UI 线程操作。请求成功、取消、失败、调用者消失及迟到回调都要有确定的资源释放路径；不能因为两个平台回调机制不同而建立第二份业务完成状态。

工程变更写入实际维护的配置、Manifest、Info.plist 或可重放生成输入，不只修改下一次生成就会丢失的工程文件。平台专用用途描述、组件、entitlement 与权限只随实际接入的能力增加。

### 2.3 Vue 与前端构建

当前项目的运行平台来自 Rust `get_platform_capabilities`，由 [platform Store](../src/core/stores/platform.ts) 持有。现有 [Vite 配置](../vite.config.ts) 尚未定义产品平台编译常量。普通文案和按钮差异继续使用这一平台事实；浏览器 UA、窗口宽度、`process.platform` 和开发电脑 OS 都不能决定手机平台。

Tauri 为前端构建钩子提供 `TAURI_ENV_PLATFORM` 等目标环境信息；Vite 可以把显式引入的构建常量静态替换并进行优化。这允许按目标裁剪前端代码，但不会自动为 Vue 增加 `#ifdef` 语法。见 [Tauri 构建配置](https://v2.tauri.app/reference/config/#buildconfig) 与 [Vite 环境变量](https://vite.dev/guide/env-and-mode)。

仅在存在真实的平台专用依赖、模块加载副作用或体积收益时引入前端编译裁剪，按以下方式集中实施：

1. 在 Vite 配置的一个位置把 Tauri 目标映射成显式类型的构建常量；只暴露需要的字段，不把整个 `process.env` 注入前端。业务组件不直接读取各式环境变量。
2. 目标缺失时，普通浏览器预览保持独立的预览语义，不默认为 Android 或 iOS。移动产物构建必须能确定实际目标，不能把预览默认值打入包内。
3. 需要彻底排除某个模块时，在模块解析或导入边界处理。`v-if`、CSS 隐藏以及未调用的函数不保证顶层 import 或模块副作用被排除；以实际产物判断裁剪效果。
4. Android 与 iOS 如生成不同前端资产，应分别构建或明确传递对应产物，不能复用上一个平台遗留的 `dist`。开发服务器切换目标也应重启。
5. 构建常量只选择随包固定的代码。系统版本、授权、设备状态和当前任务条件仍由运行时查询；发现前后端平台不匹配时报告构建或启动错误，不猜测降级到另一平台。

本项目无需为了改变“清理 WebView 缓存”的按钮说明就先建立两套前端构建，也不复制 Android/iOS 页面树、Store 或路由。确需不同的原生交互时，可以在同一业务页面下使用局部平台组件，共享同一数据 owner。

## 3. 能力事实与产品呈现分别管理

当前契约见 [Rust platform.rs](../src-tauri/src/vcp_modules/infra/platform.rs) 与 [前端类型](../src/core/types/platform.ts)：

| 字段 | 含义 | 使用边界 |
|---|---|---|
| `support` | 当前产品范围是否接纳这项能力 | `unsupported` 不自动等于 OS 在技术上永远不能实现 |
| `implementation` | 当前版本是否接通对应实现 | 用户批准开发不能直接变成 `implemented` |
| `authorization` | 原生实际观测的授权状态 | 未查询不视为拒绝，也不视为已授权 |
| `runtime` | 最近观测的运行可用情况 | 启动快照不是本次操作成功保证 |

现有 `isImplemented` / `require` 只检查支持与实现；不负责系统授权，也没有完整的领域提示文案。后续功能需要授权或动态状态时，由真实操作 owner 查询并处理，不让页面根据旧快照断言永久可用。

能力快照未加载或加载失败时，不执行依赖原生能力的动作，由现有启动 owner 处理查询及重试。不把“未知平台”当作 iOS，不用错误提示假装能力查询成功。新 WebView 按其生命周期重新取得事实，不能把前端内存当作 Rust 或系统的永久状态。

产品呈现表达另一类信息：入口是否保留、不可用时说明什么、有没有替代动作。它由最新功能决定确定，通常归所属 Feature；多个入口需要同一决策时共用一个领域函数或配置。只有真实的跨领域消费者出现时才提升到共享层，不把 24 项能力再复制成另一套可用性布尔表。

**展示与执行必须可以分别判断。**保留入口的功能，不能继续用 `v-if="isImplemented(...)"` 同时控制可见性和可执行性。也不能为使入口可见而把 capability 改成 `implemented`。

## 4. 入口与副作用的约定

| 呈现方式 | 适用情况 | 执行要求 |
|---|---|---|
| 正常操作 | 当前有实现，允许尝试 | 执行后仍处理授权拒绝、取消和运行错误 |
| 保留入口并解释 | 用户明确要求保留，如 iOS 更新、Root、语音 | 点击显示就近说明，在启动原生操作前返回 |
| 条件操作或替代流程 | 平台语义不同但用户意图相同，如 Files 导出 | 进入本平台真实流程，返回本次结果 |
| 不显示某个系统选项 | 平台没有对应设置，如 OEM 自启动权限 | 不请求、不制造“待授权”，不影响其他权限项 |
| 隐藏整项功能 | 用户已明确作出该产品决定 | 同时关闭自动入口与后台初始化，不仅隐藏按钮 |

“禁用功能并点击 Toast”应实现为可触发说明的操作行或独立说明按钮，原生执行动作保持不可用。不能对 HTML `disabled` 按钮只绑定点击提示，因为禁用后的控件不承担正常点击交互。视觉与辅助技术语义都应区分“执行功能”和“查看不可用说明”。

每条操作链遵循以下次序：读取已有平台事实 → 判断本入口的呈现/动作 → 对解释入口直接提示并返回 → 对执行入口检查能力 → 按需取得真实授权 → 调用适配层 → 由领域 owner 处理结果。原生层仍检查本次执行条件，不能信任较早的 UI 判断。

拦截覆盖点击、自动启动、定时任务、监听注册、恢复、导入设置及 AI 工具等实际入口。例如 iOS 保留更新说明，不代表要启动 APK 自动检查、下载、安装事件订阅或 OTA 保活。导入 Android 的 `enabled` 配置只保留用户配置，不能绕过当前平台的执行边界。

## 5. 命令与授权的三层边界

原生功能涉及三种不同约束：

1. **Tauri ACL**：哪个 WebView 可以调用哪个 plugin/core 命令。
2. **Rust 领域与插件边界**：当前平台有没有该操作，以及输入、路径、资源和任务状态是否允许执行。
3. **系统授权与运行条件**：当前原生请求是否允许访问相机、位置、照片等资源。

ACL 不替代业务检查或系统权限。Rust 内部调用不经过前端 ACL；UI 隐藏也不能保护直接 invoke 或 AI 工具。现有 app 命令继续经 [commands.rs](../src-tauri/src/commands.rs) 中央分发和 `main` WebView 限制；自有插件命令按 [插件局部规范](../src-tauri/plugins/vcp-mobile/AGENTS.md) 注册和授权。Tauri 平台 capability 的含义见 [官方能力文档](https://v2.tauri.app/security/capabilities/)。

只有已接通且存在真实前端消费者的插件命令才增加平台 ACL。用于内部 Rust→Swift 的接口不因“iOS 功能已实现”自动开放给 Vue；说明入口也无需放开原生权限。

同一用户意图如果有相同的输入、结果和生命周期，优先保持共享业务接口，由适配层实现差异。例如“导出文件”可以在 Android 保存到下载目录，在 iOS 让用户选择 Files 目的地。APK 安装、Android task 退后台、Root/PTY 等机制不同的操作，保留明确的平台语义，不给 iOS 伪造同名成功。

共享接口的结果必须能表达实际差异：用户取消与失败分开；未获得目标路径时不虚构路径；缺少某遥测字段时不填假值。需要调整 DTO 时，沿实际 producer、Rust、Vue 或 AI 消费者一起更新，不只修改一端声明。

## 6. 共同权限引导与按需请求

按 09 的审批方向，权限引导可以共享外壳、说明和恢复入口，具体项目来自各平台已经实现的权限能力。`androidPermissionGate` 当前仍是 Android 专属契约，不能直接在 iOS 挂载原 Android Gate 或调用 `check_all_permissions` 就称为共同引导。

- iOS 无对应 API/设置的项目不出现。Android 通知监听、OEM 自启动和电池豁免不能翻译成不存在的 iOS 开关。
- 引导展示状态与真正请求授权分开。只在相关功能已实现、用户主动使用或明确选择授权时发起必要请求；可选功能被拒绝，不自动阻断聊天和文本输入。
- 系统首次未询问、用户拒绝、系统限制、有限授权等状态按实际功能需要保留。现有四值 `authorization` 无法表达所需区别时，在消费该区别的原生接口及 DTO 上完整扩展，不把不同状态压成一个错误的 `denied`。
- 从系统设置返回后，由该权限的 owner 刷新真实状态。只有实际存在、可用的设置跳转才能作为恢复动作。
- 本 App 的本地通知、远程推送/APNs、读取其他 App 通知是不同能力；批准系统通知适配不自动批准整个推送服务或通知监听架构。
- Files/图片选择、相册写入、相机、麦克风分别按实际 API 定义访问范围，不复制 Android 全部存储权限门禁。局域网路径在线也不证明 LAN 已授权或目标服务可达。

## 7. 错误与用户提示

执行边界返回机器可识别的原因，界面按操作上下文组织文案。预期不可用由点击所在入口解释；已进入业务流程的失败由现有领域结果 owner 告知。下层记录诊断，不在每一层都弹 Toast；自动重试、轮询和快照回放也不能重复制造用户通知。

以下是语义分类，不要求立即新建全局错误枚举或改写所有 IPC：

| 原因 | 应表达的含义 | 不应给出的指引 |
|---|---|---|
| 平台机制不适用 | “APK 应用内安装仅适用于 Android；iOS 请在应用外自行签名安装。” | 去 iOS 设置打开未知来源 |
| 已决定接入但当前未实现 | “当前 iOS 版本尚未提供语音输入，可继续输入文字。” | 要求开启麦克风来修复未实现代码 |
| 本次系统版本/设备不支持 | 说明具体操作的适用条件，提供真实替代流程 | 混称整个 iOS 平台不支持 |
| 未获授权或访问受限 | 说明被限制的操作与实际可用的恢复方式 | 报成尚未适配、文件损坏 |
| 用户取消 | 返回原界面，清理本次临时资源 | 失败 Toast、常驻错误或自动重试 |
| 条件暂不可用 | 说明当前网络、空间、前后台等真实条件 | 宣称重新授权一定有效 |
| 原生或业务执行失败 | 说明影响与可执行的下一步，保留诊断 | 用笼统“平台不支持”吞掉错误 |
| 等待超时 | 说明当前未取得结果，并按实际任务语义处理 | 把超时直接等同操作取消或底层失败 |

当前 Rust 平台边界已有 `unsupported:` / `not_implemented:` 字符串错误；`Result<T, String>` 仍遵循仓库规范。改造提示时，稳定原因在边界产生并在一个消费位置解析，不在多个组件按完整英文句子匹配。现有信息不能区分所需原因时，只对涉及的调用链增加编码和解析，不以文案重构为由建立无消费者的通用错误系统。前端的 `notImplemented` 能力枚举与错误前缀是不同契约，不混写。

提示内容包含“当前操作为什么不能完成”和“用户现在能做什么”。普通未实现功能在主动触发时就近说明，不逐项产生启动警报或常驻失败通知。真正持续影响应用运行的故障按现有通知 owner 处理；R2/R3 的具体通知生命周期由对应实现任务闭合。

成功文案使用真实操作结果。导出按钮的描述、处理中状态、完成提示和下一步动作要一起检查，不能只把按钮从“下载目录”改成“Files”，成功时仍硬编码 `下载/VCPMobile`。缓存清理同样明确清的是 WebView HTTP 缓存、业务缓存还是用户数据，不因平台 API 名称相似就扩大删除范围。

未知底层错误不能原样暴露路径、密钥或请求内容；面向用户给出操作级说明，必要诊断进入现有日志通道。不要编造平台原因来替代未知错误。

## 8. 部分能力与后台任务

Distributed 兼容以真实工具和字段为单位。整体入口可用不代表 14 个工具全部等价；工具可注册也不代表每个字段都能读取。保留已取得的数据，对缺失、未实现、未授权或不适用的项目给出可区分结果；不得用 `0`、空字符串或 Android 模拟数据充当成功测量。合法的零值仍是数据，不能反过来全部当作缺失。

AI 的工具发现/描述和执行路径应表达同一能力范围，并在真正执行时重新检查。单个工具或字段不可用不应使其他已实现工具全部失效；也不能为保持一个完整面板而伪造所有指标。`networkStatus` 的逐字段可行性需要单独核对，现有 NWPath 连通事件不等于 IP、速率等完整遥测。

用户在 09 中将 SSE 后台持续接收列为重点要求，并提出静音播放等候选方式。后台专项需要分别研究“保持执行”“断开后的恢复/对账”和“最终结果持久化”，记录每种方案的系统条件、资源消耗、中断和清理行为；不能把有后台 API 或声明某种模式解释为无限执行保证。Apple 的后台机制按任务类型和系统调度划分，见 [后台策略说明](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)。本规范不预先采纳或排除某个候选实现，也不把这一重点需求降格成已经满足的尽力后台。

## 9. 本轮功能审批如何进入开发

[Phase 2 的 09 审议表](../plan/vcpmobile-ios-compatibility-research/phase-2/09-功能权限与提示审议表.md) 中用户新增的逐项意见，优先于同文档尚未更新的旧建议和早期延期列表。09 保留审批原文；下表归纳会影响跨平台开发方式的决定，不指定所有功能必须在 Phase 2 完成。

| 审批主题 | 后续开发必须体现 | 仍需专题设计的部分 |
|---|---|---|
| APK 更新、Root、语音 | 保留入口；iOS 对不可执行的动作先解释并返回 | 各入口与自动路径的完整覆盖；语音仍未开发 |
| 共同权限引导 | 共享引导结构，按实际平台 API 列项 | 原生权限模型、拒绝与恢复，不直接复用 Android 权限命令 |
| 电量、空间、常亮、WebView 缓存 | 按真实原生 API 适配；平台差异反映到结果和按钮描述 | API 可得范围、缓存清理范围、常亮资源释放 |
| incoming share、系统通知 | 按本轮意见纳入适配研究与实施安排 | 分享生命周期/工程结构；本地通知与远程推送的具体范围 |
| 相机、保存相册、向外分享 | 按原生能力接入，沿同一媒体/文件业务链处理 | 权限、取消、格式与临时文件生命周期 |
| 网络遥测、Distributed | 兼容整体功能，逐工具、逐字段真实报告 | 各平台 API 覆盖和缺失数据表达 |
| SSE 后台持续接收 | 作为后台专项重点目标 | 候选保活、恢复和持久化方案的效果与边界 |
| CLI、根返回及其他未更改项 | 延续各项明确决定，不因本轮规范自动开放 | 只有新需求才扩展不同运行时或交互语义 |

“可以做”“存在 API”确定的是开发方向，不能据此认定完整技术链已解决。分享扩展、系统通知、完整遥测和后台执行分别有自己的设计范围；批准接入后可更新 `support`，只有真实实现闭合后才能更新 `implementation`。没有新决定的 U1 关于页方案等仍不自动生效。

## 10. 实施顺序与验证

每个功能先在所属计划或变更说明中写清：用户意图、Android 现状、iOS 目标、入口呈现、权限/运行条件、成功/取消/失败结果，以及状态与资源的唯一 owner。简单功能用短段落即可；只有跨进程、任务恢复、复杂资源生命周期等问题才需要独立方案，不为每个按钮重复整篇架构文档。

落地顺序通常是：领域契约和平台适配 → 真正的命令防线及所需 ACL → 能力事实 → UI 入口和文案 → 对应验证。纯提示改动可以先完成解释入口，但不得提前开启原生能力。提交前沿真实调用链核对自动启动、导入配置、恢复与 AI 调用，避免只完成点击路径。

| 本次改变了什么 | 应取得的证据 | 证据不能代替什么 |
|---|---|---|
| 仅规范或功能决定 | 对照用户意见、现有入口和链接检查 | 不证明产品行为已改变 |
| Vue/Rust 跨层或核心逻辑 | `pnpm check`；按改动选能暴露真实错误的行为验证 | host 检查不覆盖 iOS 专属 cfg 或 Swift |
| 插件 Rust 边界 | `cargo check --locked -p tauri-plugin-vcp-mobile`，必要时检查实际目标分支 | host 假数据不证明原生接口工作 |
| Android Kotlin/Manifest/Service | 编译实际 Android 插件目标；行为结论按需取得指定 Debug 设备证据 | 构建不证明权限交互或后台持续性 |
| iOS Rust/Swift/原生工程 | Windows 追踪源码、SDK 条件、调用与释放；阶段性 G1/G2 取得 Apple 编译/链接证据 | 不宣称已经观察到 Scene、系统授权或后台运行行为 |
| 前端平台裁剪或 WebKit 兼容 | 核对目标输入与实际生成 JS/CSS/模块 | `v-if` 或源码字符串断言不证明产物被裁剪 |

验证服从当前不确定性。可用的反例包括：解释入口意外启动下载；导入设置绕过门禁；拒绝权限却显示未适配；取消被当作失败；一项遥测缺失导致全部数据丢弃。选择与本次改动有关的场景，不把文档表格、枚举和测试 fixture 互相复制后当作额外正确性证据。

iOS 保持当前项目边界：日常源码审计，Apple 构建仅通过手动 G1/G2，不建设实机测试体系。交付明确区分源码判断、host 检查、Apple 构建和实际运行事实，尚未取得的证据不写成通过。

当前推进关系：R2/R3 由独立任务负责；本规范指导后续能力和呈现改造。优先闭合已决定的解释入口与能力事实差异，再按依赖安排文件/媒体、共同权限、系统分享/通知、设备工具和后台专项，保留 Android 已有生产行为。
